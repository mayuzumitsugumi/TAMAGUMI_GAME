# TAMAGUMI：最低成本開發架構與流程

更新：2026-10-24。狀態：規劃完成，尚未實作或驗證建置。

## 1. 目標與邊界

- Android：主要開發及首發目標，提供 APK，暫不上 Google Play。
- iOS：次要目標，候選為 HTML5／PWA；若不可行先發布 Android，再研究調整。iOS 測試與修正不阻擋 Android 首發。
- 養成進度存在玩家裝置；備份由玩家匯出到自己的儲存位置，再自行匯入。
- 不託管玩家養成資料；第一階段不建立帳號、資料庫、雲端 API 整合或自動同步。
- 不使用廣告、內購、分析追蹤、健康感測器與即時連線服務。
- 兌換機制、正式養成規則與 UI 細節延後討論。本輪不固定角色切換、成長或死亡玩法。
- 角色方向已知為台灣紫嘯鶇與人型；128×128 為素材候選基準，不決定兩者玩法關係。

最低成本指工具費、開發返工、下載流量、服務維運及測試總成本，而非只比較主機月費。

## 3. 技術決策

暫定一份乾淨的 Godot 4 穩定版 GDScript 專案，先完成 Android，再驗證 Web；核心與備份格式保持可移植。
固定編輯器與 export templates 版本；先做技術驗證，再鎖定具體小版本。不因參考專案而綁定 Godot 4.3。

2026-10-24 透過官方 GitHub releases/latest 核對為 [4.7.2-stable](https://github.com/godotengine/godot/releases/tag/4.7.2-stable)，發布於 2026-08-18。列為安裝驗證候選，尚未實際安裝或建置，不據此宣稱相容性通過。

- 使用 Compatibility renderer、2D、Web 單執行緒匯出。
- Android 原生輸出 APK；不用 WebView 容器，避免增加一套 Capacitor／Cordova 工具鏈。
- Web 加薄層 JavaScript 處理檔案選取、匯出／可用時分享，以及瀏覽器生命週期。
- 先用 Godot 內建能力；必要時才新增小型平台橋接，逐一評估授權與維護。
- 素材先使用佔位圖；不開發完整素材匯入外掛，也不自訂精簡引擎模板。
- 不加入空的兌換、雲端或帳號系統。以穩定內容 ID 保留日後擴充能力即可。

Phaser／TypeScript＋Android 容器作為替代評估路線，不與 Godot 同時完整開發。
只有在首輪量測證明 Godot 的載入、大小或 Safari 相容性不符需求時，才以同一驗收案例比較替代方案。

## 4. 模組分工

```text
呈現層（佔位畫面／未來正式 UI 與動畫）
                 ↓ 操作                  ↑ 結果事件
應用協調層（啟動、操作、還原、暫停／恢復）
                 ↓
純資料養成核心（資料＋操作＋時間 → 新資料＋事件）

應用協調層 → 共用存檔編碼／驗證／遷移 → 平台保存與檔案介面
                                            ├─ Android：user://、系統文件操作
                                            └─ Web：user://持久化、瀏覽器匯入／匯出
```

- 核心不讀檔、不取得系統時間、不引用 UI 節點或播放動畫；使用 GDScript 純資料物件。
- 時間由協調層傳入；前景及離線使用同一規則入口。具體規則稍後定義。
- 結果與顯示分離，動畫中斷不取消已完成的資料操作。
- 保存流程可回傳錯誤與狀態；本機保存、檔案匯出、雲端上傳不是同一種成功訊息。
- 平台能力以介面提供，核心不散布 Android／Web 分支。

預定目錄（目前不建立空程式檔）：

```text
core/          資料模型、操作與時間推進
application/   流程協調
persistence/   編碼、驗證、遷移、還原
platform/      Android／Web 儲存及檔案適配
presentation/  場景、動畫與 UI
content/       內容 ID 與設定資料
tests/         核心與資料互通測試
web/           HTML shell 與必要 JavaScript
docs/          規格、決策、測試與參考來源
```

## 5. 共用備份契約

初期使用 UTF-8 JSON，副檔名暫定 `.tamgbackup`，MIME `application/json`。
不先加入 ZIP、資料庫或備份密碼，避免增加依賴與恢復成本。副檔名與格式定案後須版本管理。

封包至少包含：

| 欄位 | 用途 |
|---|---|
| `format` | 固定識別備份類型 |
| `schema_version` | 格式版本，控制驗證與遷移 |
| `app_version` | 來源 App 版本，供診斷 |
| `save_id` | 存檔字串識別碼 |
| `revision` | 同一存檔的修訂序號；不能單獨用於跨機衝突裁定 |
| `exported_at_utc` | UTC 匯出時間，用於展示，不作可信防作弊時間 |
| `last_simulated_at_utc` | 最後完成結算時間，避免重複補算 |
| `payload` | 版本化遊戲資料，玩法討論後細定 |

- 全部時間使用明確定義的 UTC Unix 秒整數；非有限浮點值拒絕。整數不超過 JavaScript 安全整數範圍，ID 用字串。
- 不保存 Node、Resource 實例、平台絕對路徑、授權憑證或美術二進位資料。
- 內容由穩定 ID 引用；未知必要內容不能悄悄刪除後回存，需明確拒絕或依版本策略保留。
- 同一套編碼、驗證、遷移邏輯供兩平台使用，不做兩種格式或兩個獨立轉檔器。
- 匯入先限制檔案大小／深度並驗證完整欄位；未知新格式拒絕，舊版依明確遷移升級。
- 先在暫存資料完成驗證，保留還原前副本，成功保存後才切換目前狀態。
- Android／Web 使用相同邏輯交易流程，底層持久化機制分別驗證，不假設 rename 就等於瀏覽器完成落盤。
- 第一版不合併兩台進度；匯入需確認。備份不是加密、防作弊或一次性移機機制。

## 6. 保存及玩家備份

### 本機自動保存

重要資料變更後保存；一般變更去抖並定期保存。暫停／隱藏時盡力補存，但不依賴關閉事件。
恢復時避免重複計算時間；初期保留目前及上一份有效本機狀態。

Web 的 `user://` 會涉及 IndexedDB 持久化。須驗證實際引擎版本的同步與失敗通知，不以 `store_string()` 返回便宣稱持久保存完成。
若 API 無法可靠確認，保存狀態顯示須反映限制；重載驗證與手動匯出是必要補強。

### 玩家手動備份

- Android：由遊戲產生封包，開啟系統文件儲存／分享；還原以文件選擇器取得資料。
- Web：由使用者點擊觸發匯出，支援時分享檔案，否則下載；匯入用檔案選取。兩條路均須驗證。
- 不要求玩家尋找遊戲私有目錄；填入可辨識檔名與日期，不把個人資訊放入 URL。
- 玩家選擇雲端 App／檔案提供者；不整合雲端 OAuth，不代管雲端帳密。
- 僅記錄「備份已匯出／已交給分享介面」，不能推論遠端上傳已成功。
- 不承諾背景自動覆蓋任意雲端檔案；系統及提供者支援不同。
- 本機兩版備份有固定上限；匯出的日期檔由玩家自行管理，App 不能保證刪除玩家雲端舊檔。

## 7. 發布與成本

第一階段只需靜態檔案託管，無遊戲後端、資料庫、常駐運算或玩家存檔流量。

| 項目 | 成本與策略 |
|---|---|
| Godot／GDScript | 不需引擎訂閱費；發行時保留必要引擎聲明 |
| Aseprite | 玩家提供美術；既有工具授權依持有情況處理 |
| APK 散布 | 檔案託管／下載流量；簽署金鑰需安全保存與備份 |
| Web／PWA | HTTPS 靜態託管、資源下載流量；免費額度不等於無限 |
| 網域 | 可先用供應商子網域；選好正式來源再公開，換來源會影響本機資料存取 |
| CI | 初期本機／手動可重現建置，頻率增加才評估免費 CI 額度 |
| 測試 | Android 與 iPhone 真機時間；iOS 由使用者朋友協助 |

候選為 GitHub Pages 或 Cloudflare Pages 等靜態託管，但在查核當期條款、用途、大小與流量限制後才選定；本輪不建立帳號或發布。
APK 下載空間依相同條件另選，不假定靜態網站供應商適合存放大型安裝包。

每次量測分別記錄 APK 大小、Web 壓縮傳輸量、未壓縮體積、首次／暖啟動時間及更新下載量。
估算月流量：冷載入次數 × 每次傳輸量 ＋ 更新下載量 ＋ APK 下載次數 × APK 大小。
例：20 MB × 1,000 次冷載入約 20 GB；只是計算示例，不是本遊戲量測或價格。
PWA 快取可減少重複下載，但不能保證永不被清除。先量測，再決定是否需要精簡模板或其他引擎。

### 新增候選玩法與範例審查

使用者貼出的搜尋討論提出「狀態耗盡回到蛋、點擊孵化」；先記為候選，觸發條件、影響哪些進度、人型與鳥形關係及衰退速度均待玩法討論，不直接採用一小時扣光等示例數值。

- AnimatedSprite2D、CanvasLayer、Container及signals適合呈現層；Timer不是持久化時間來源。
- Pet透過相對路徑直接存取HungerBar會耦合UI，正式程式改由協調層及事件更新。
- ConfigFile可用於音效等設定；遊戲進度與通用備份仍使用同一JSON契約。
- 前景用單調時間增量；離線使用保存的UTC結算時間，重複焦點通知不得重複套用。
- Android處理PAUSED／RESUMED及必要焦點事件，但定期／重要變更保存仍是基礎。
- 孵化／吃飯不能依賴await計時完才永久記錄結果，須定義中斷可恢復的交易與狀態。
- 將負時差歸零只是異常處理，不是可靠防作弊；user://也不表示資料自動加密或可跨機恢復。
- Nearest保留像素邊緣，但canvas_items＋keep不保證整數縮放；正式畫面策略待UI原型驗證。
